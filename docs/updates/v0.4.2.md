# Synchri v0.4.2 — Round 4: managed agents, the side-task dropbox & planning mode

This document opens the v0.4.2 round, marks the baseline it builds on, and
records the agreed scope and its governing decisions. It is the handoff
artifact for the implementation that follows: the scope below went through
several rounds of adversarial review and is intended to be
decision-complete — an implementer should not need to invent policy, only
build and test it.

## Baseline

- **Previous version: v0.4.1**, tagged at commit
  `283f600cf9b955120cb5485db49d1c7681ea9e06`.
- This round ships as **one update, v0.4.2**, developed on branch
  `claude/synchri-0-4-2-update-i8h36g`.
- **Stream order is A → B → C.** The Dropbox's ancillary scouts and
  reviewers (Stream B) and Planning Mode's automatic team provisioning
  (Stream C) both depend on Synchri owning and verifying the agent-CLI
  lifecycle first (Stream A).
- Relevant machinery that already exists at the baseline: managed one-shot
  launch commands for Claude Code / Codex / Copilot
  (`synchri/session/modes.py`), the conductor and managed-session registry
  (`synchri/runner/conductor.py`, `synchri/runner/managed.py`), streamed
  ingestion, per-agent restart, the two-strike drop, and escalations
  (v0.4.0). `runtime_status()` today is only an executable-on-PATH check;
  the ready-to-paste join prompt is still the UI's instruction for agents
  Synchri does not launch; supervision (workers, cancellation, process
  groups) is session-scoped; the conductor exits when the room goes idle;
  and any edit to a `ProductSpec` changes its digest and forces a new
  contract acknowledgment. The scope below is written against those facts.

## Product principles

- *"Users should supervise the objective, not supervise the existence of
  the agents."*
- *"Planning should be executable state, not prose the user has to carry
  into the next workflow."* — in short: plan it, review the plan, approve
  it, Synchri staffs and executes it.

## Scope — 22 items

### Stream A — Managed Agents

- [ ] 1. **Passive connection doctor.** A side-effect-free, timeout-bounded
  check per known runtime that can run freely (boot, runtime chooser):
  executable present, version parsed and inside the supported range,
  capability flags, and a cached-auth **indication** only. It never invokes
  the provider, never incurs charges, and every check reports an honest
  pass, fail, or unknown — never a fake green.
- [ ] 2. **User-initiated connection test.** With explicit consent, a real
  bounded CLI invocation proves the whole managed path: unattended launch,
  bootstrap injection, structured-output parsing, and auth validity. Where
  the runtime advertises resume, the test is **two invocations** — the
  first emits a session/resume ID, the second resumes it — because one
  invocation cannot prove resume; no resume support, or a failed second
  step, is recorded honestly as `unsupported` or `supported-unverified`
  (verified at first real recovery). Canary invocations run in a fresh
  temporary directory outside every repository, with a fixed sentinel-only
  prompt and no repository mutation authority; they are cost-bounded,
  hard-timed-out, and cancellable. The durable per-runtime "connected"
  record is **invalidated** whenever the executable path, version, adapter
  revision, or auth validity changes; the passive doctor re-checks those
  cheaply on boot and downgrades to "reconnect needed".
- [ ] 3. **First-run sign-in walkthrough.** Setup walks the user through
  signing into each CLI once, then verifies via the connection test. The
  doctrine: Synchri owns no provider account, stores no provider credential
  or API key, and uses no cloud relay; authentication remains inside each
  provider CLI.
- [ ] 4. **The paste step is gone for connected agents.** Starting a session
  becomes: select your agents → give your spec → Start. Synchri launches
  the selected runtimes in the right worktree, injects each agent's
  role-specific contract/bootstrap, verifies acknowledgment, marks them
  ready, and begins the room automatically. The user never sees or pastes a
  join prompt for a connected runtime; the ready-to-paste flow survives
  only for genuinely external/unconnected agents. The retired wizard stays
  untouched.
- [ ] 5. **Join-phase indicators and partial joins.** Joining can take a
  minute, so from Start until the room is live the UI shows per-agent
  assembly status driven by real phase transitions — launching → injecting
  bootstrap → awaiting acknowledgment → ready — and the indicators go away
  once all agents are officially ready. If one agent becomes ready and
  another fails, the room stays inactive, ready agents remain attached and
  receive no work, and retry targets only the failed participant.
- [ ] 6. **Participant-scoped supervision.** Workers, cancellation, process
  groups, recovery generations, and provider resume IDs move from session
  scope to per-participant scope. Today "Restart agent" restarts the
  managed team; the recovery ladder below cannot operate per-agent without
  this change.
- [ ] 7. **Failure discrimination and the recovery ladder.** Agent-process
  failures are classified as auth failure / provider refusal / crash /
  normal stop / unresponsive — distinct durable per-agent states with
  distinct chat/rail presentation. Recovery walks: resume via the stored
  resume ID where supported → relaunch → replace with state reconstructed
  from the durable room (contract, role doctrine, transcript tail, gates)
  → escalate only when recovery genuinely requires the human (expired
  auth, hard provider refusal, repeated relaunch failure). The ladder
  composes with the existing restart flow, two-strike drop, and
  escalations: exactly one supervisor decision per failure.

### Stream B — the Dropbox (side-task system)

- [ ] 8. **Add task.** During a live session the user captures a side idea
  as a dropbox item (`DROP-NNN`) with a bounded prompt, without
  interrupting the main agents or the active contract. Capture freezes when
  original-gate evaluation / completion validation begins, so extension
  chains cannot grow forever.
- [ ] 9. **Scout and adversarial review.** An ancillary scout agent
  (launched with Stream A machinery) investigates the item in parallel, off
  the critical path, and deposits a structured proposal into the shared
  inbox: evidence, rationale, optionally a patch/commit, and a
  recommendation. An ancillary adversarial reviewer attacks the proposal
  before promotion — mandatory by default, skippable only by explicit
  per-item user choice recorded in provenance. The proposal is an immutable
  digest over its contents **including the scout's `base_sha`**.
- [ ] 10. **Ancillary execution limits.** Ancillary work runs in its own
  room/process, separate from the main room, in a scratch worktree based at
  the main session worktree's HEAD at scout start, on branch
  `synchri/drop/<session>/<drop-id>`, with no push, no merge, and no
  canonical-worktree permission. Defaults (configurable): one scout plus
  one reviewer concurrent; scout budget 15 minutes wall-clock or 12 turns,
  reviewer 10 minutes or 8 turns, whichever arrives first; one automatic
  retry per stage, further retries user-initiated. Failed work has a
  terminal route: timeout, budget exhaustion, or crash produces a
  `failed`/`timed_out` disposition with a failure report, so mandatory
  evaluation can never block completion forever.
- [ ] 11. **Artifact bounds, fail-closed.** Evidence/rationale ≤ 64 KB;
  stored patch ≤ 256 KB. Secret scanning at deposit is fail-closed: a
  detected secret causes the patch to be omitted/quarantined, and raw
  sensitive content is never persisted, streamed, or included in the
  completion package (whose existing contract already forbids
  credentials). An oversized patch is not stored — the proposal carries a
  diffstat plus a bounded preview, and the scratch branch is retained until
  its extension is completed, the item is explicitly rejected, or the patch
  is imported into the session worktree (approval is when the main pair
  first becomes authorized to use it, so retention must outlive
  evaluation). Cleanup order everywhere: the durable proposal is captured
  first; scratch worktrees/branches are removed on decline, failure, or
  session deletion, and otherwise once the retention rule releases them —
  ancillary branches are ephemeral by contract, exempt from the
  session-worktree "only remove when provably safe" rule, which protects
  the user's worktrees.
- [ ] 12. **Dropbox reconciliation.** There is no periodic scheduler loop
  today and the conductor exits on idle, so reconciliation is an explicit
  hook: it runs (a) after each completed main-agent turn and before the
  next queue activation, inside the managed run loop, and (b) immediately
  when an item is captured, so an idle room cannot miss it. Reconciliation
  appends ready items to the appendix **exactly once**, guaranteed by a
  database uniqueness constraint on `(session, drop_id)`.
- [ ] 13. **Appendix, not spec revision.** The original `ProductSpec` is
  stored unchanged — editing it would change its digest and force every
  participant to re-acknowledge a new contract, interrupting the room. The
  appendix is a separate append-only stream rendered after the spec. The
  spec created at room creation stays the source of truth; appendix items
  are explicitly *additional but not optional*: every one must receive an
  explicit evaluation after the original task is complete, nothing is
  silently dropped, and none may interfere with the development of the
  original spec.
- [ ] 14. **Evaluation and dispositions.** Both current main roles evaluate
  the same immutable proposal digest and both evaluations are recorded:
  both approving means approved; any non-approval means declined, with both
  rationales retained. A replacement participant holding a main role may
  supply a missing evaluation (approval is role-based; provenance records
  the participant and its recovery generation). Approved items become
  contract extensions — `DROP-017 → APPROVED → EXT-004` — whose gates are
  materialized atomically before completion validation. Declined or failed
  items record their rationale or failure report and never block closing.
  Ancillary patches are never applied or cherry-picked automatically: the
  main pair may use one only after approval, working inside the session
  worktree.
- [ ] 15. **Durable session phases and provenance.** The session carries a
  durable phase: `original_work → appendix_evaluation → extension_work →
  closing`. In `original_work`, a valid completion request transitions
  atomically to `appendix_evaluation` — it does not close the session —
  and capture freezing plus the dropbox snapshot happen in that same
  transaction. All snapshot items must reach a terminal disposition before
  `extension_work`; approved extensions execute in appendix order, and
  approving one enqueues work and wakes the main agents (the conductor
  exits on idle, so extension work restarts the loop rather than waiting
  for it). Only `closing` may invoke today's terminal room-closing
  behavior. Session semantics overall: original contract → original gates
  complete → appendix evaluated → approved extensions execute → extension
  gates complete → session closes. Provenance minimums: gates, events,
  usage, proposals, and completion-package records carry `origin_kind`
  (main vs. ancillary), `drop_id`, and optional `extension_id`; the usage
  summary reports ancillary work separately, never merged into ordinary
  participant totals; the inbox UI shows each item's lifecycle (captured →
  investigating → reviewed → appended → evaluated).

### Stream C — Planning Mode → approved coordination

- [ ] 16. **Planning Mode as a native workflow — and the spec on-ramp.**
  The `ProductSpec` required to start coordination is a friction point for
  a user who does not know how to put one together, so Planning Mode gives
  them a place to articulate the idea instead: New session → Plan → choose
  repository/workspace → articulate the idea in as much or as little
  detail as they want (free-form, stored verbatim) → choose planner + plan
  reviewer → Start. It is a new mode entry in the existing mode-policy
  table, not a document-generation feature. Two roles, neither with
  implementation authority while the session is in Planning Mode:
  the **Planner/Architect** inspects the repository, current
  implementation, dependencies, constraints, acceptance criteria,
  migration risks, likely failure modes, and testing and preservation
  requirements, then produces an ordered implementation plan; the
  **Adversarial Plan Reviewer** independently reviews implementation logic
  rather than restating it — challenging ordering, hidden dependencies,
  unnecessary reconstruction, missing rollback/migration concerns,
  insufficient tests, conflicting assumptions, unsafe sequencing, and
  places where existing behavior should be preserved instead of changed.
  Isolation is capability-based, not contract-only: planning runs in a
  disposable planning workspace anchored to an `inspection_sha`, and a
  runtime adapter must declare a `read_only_planning_workspace` capability
  that technically confines writes to the disposable analysis area.
  Planning Mode is offered only on runtimes with that capability;
  unsupported runtimes are shown as unavailable, never silently downgraded
  to contractual denial. The workspace's Git state is verified after every
  turn as defense-in-depth, and the workspace is never reused for
  coordination.
- [ ] 17. **The review loop — planner drafts first.** The first pass is the
  planner alone turning the user's articulation plus repository inspection
  into a draft; only then does the reviewer receive it. The loop is
  `PLAN-DRAFT → ADVERSARIAL REVIEW → REVISION → RE-REVIEW → PLAN-READY`.
  The planner may defend a decision when evidence supports it, revises when
  the reviewer identifies a valid problem, and explicitly records
  unresolved forks when multiple approaches remain genuinely defensible.
  PLAN-READY requires adversarial-review closure, not merely planner
  completion: open blocking objections or unresolved architectural forks
  prevent PLAN-READY and approval; nonblocking assumptions may remain,
  clearly classified. A human edit, or a dropbox item promoted into the
  planning session, invalidates PLAN-READY, creates a new revision, and
  requires re-review. The loop has a mechanical terminal route with
  numeric defaults: 24 agent turns, six plan revisions, or 60 minutes —
  whichever arrives first — with one user-authorized resume; exhaustion
  produces `needs_human_resolution`, preserving the latest draft and open
  objections rather than looping forever. During planning the UI shows the
  current plan revision, planner status, reviewer status, outstanding
  objections, resolved objections, unresolved architectural forks, and
  plan-readiness.
- [ ] 18. **The durable plan artifact `PLAN-NNN`**, preserving at minimum:
  the user's original idea articulation, verbatim; objective and scope;
  current repository facts; explicit assumptions; ordered implementation
  steps; affected files/components where known; dependency ordering;
  preservation requirements; migration/data-state considerations;
  security/reliability considerations; test and verification requirements;
  acceptance criteria and derived gates; identified risks; reviewer
  objections and their dispositions; unresolved questions requiring human
  judgment; and provenance showing planner, reviewer, revisions, and
  timestamps. The final artifact clearly distinguishes the original
  proposed plan from changes introduced through adversarial review.
- [ ] 19. **Approval is a state transition** — `PLANNING → APPROVED_PLAN →
  COORDINATION` via a clear *Approve & Start Coordination* action, not a UI
  acknowledgment. A session's mode, room, worktree, and contract history
  are immutable at creation, so approval **creates a new, linked
  coordination session**; the planning session and the approved `PLAN-NNN`
  remain immutable, and there is exactly one coordination session per
  approved plan. The transaction boundary is concrete: first, one
  transaction reserves a unique promotion/coordination record, freezes the
  plan-revision digest and dropbox routing, and records the approved SHA;
  then the worktree, room, contract, and agents are provisioned resumably —
  a retry resumes that record, never creating or cleaning up a second
  session. At approval Synchri revalidates the repository baseline against
  the `inspection_sha`: drift returns the plan to review rather than
  silently executing stale assumptions. The coordination worktree branches
  from that frozen `inspection_sha` exactly — retries reuse the recorded
  SHA even if the source branch has since moved. Approval also atomically
  freezes dropbox capture for the planning session; an item captured after
  approval but before coordination activation enters the new coordination
  session's dropbox.
- [ ] 20. **Plan-to-contract conversion is exact.** Approval freezes one
  plan revision digest. Objective, scope, ordered work, constraints,
  preservation requirements, explicitly identified acceptance criteria,
  accepted implementation-affecting assumptions, and resolved reviewer
  findings form `ProductSpec` v1 via a deterministic serialization — agents
  must never be told to follow constraints that are not part of their
  canonical contract. Only superseded objections and review history remain
  linked provenance, along with the verbatim idea. Acceptance criteria map
  to gate IDs deterministically — never through the generic prose
  extraction, which can collapse a plan into a lone `SPEC-01` gate — and
  promotion fails if required criteria are missing or gate IDs collide.
  Blocking decisions cannot cross approval: the user must resolve or
  explicitly waive each one, producing a reviewed revision; only
  nonblocking assumptions and deferred advisories transfer into
  coordination. The coordination session auto-populates everything else —
  repository context, the explicitly selected worktree policy,
  implementation order, provenance back to `PLAN-NNN` — with no copying,
  pasting, re-prompting, second setup wizard, or manual gate regeneration:
  on this path the user never writes a `ProductSpec` by hand. Staffing: by
  default the connected planner and reviewer are reused, remapped to
  builder and implementation reviewer; an optional compact staffing choice
  sits before approval, never a second wizard. Stream A machinery then
  provisions the team automatically.
- [ ] 21. **Execution semantics and drift governance.** The builder
  implements against the approved plan; the implementation reviewer runs
  the existing adversarial build-review loop. Deviations from the approved
  plan are explicit, never silent: materially necessary divergence is
  recorded with rationale and — where it changes scope or acceptance
  criteria — becomes a contract revision; ordinary implementation detail
  that does not alter the approved plan's meaning needs no human approval.
  The planning reviewer's approval is not implementation sign-off: plan
  correctness and implementation correctness remain separate evidentiary
  stages.
- [ ] 22. **Composition with the Dropbox.** A dropbox item promoted during
  a planning session becomes an additional reviewed planning consideration
  before PLAN-READY. An item promoted after coordination has begun follows
  the standard `DROP-NNN → APPROVED → EXT-NNN` semantics, appended after
  the original approved execution contract — the approved plan is never
  rewritten retroactively.

## User-confirmed decisions

- One update, three streams, implemented in order: Managed Agents, then the
  Dropbox, then Planning Mode.
- Once a CLI is connected, the user never pastes a join prompt: select
  agents, give the spec, Start. Join indicators stay up until the agents
  are officially ready, then go away.
- Dropbox work is non-authoritative by default. It cannot silently alter
  the main contract or merge into the canonical branch; it returns
  evidence, rationale, possibly a patch/commit, and a recommendation.
  Approval by both main roles is the only path to authority.
- The dropbox check is an explicit part of the coordination cycle. Items
  are appended to the bottom as an appendix; the spec created at room
  creation is the source of truth; appendix items are additional but not
  optional, evaluated after the original task is complete, and must never
  interfere with the original spec's development.
- Humans are interrupted only when recovery genuinely requires them.
- Planning Mode exists so users can articulate an idea without knowing how
  to write a spec; the planner drafts first, then the reviewer attacks the
  draft; approval instantiates the plan as execution state with nothing
  copied, pasted, or regenerated by hand.

## Acceptance scenarios

Implementation must demonstrate, with tests, at least:

- Connection invalidation: an executable-path, version, adapter-revision,
  or auth change downgrades "connected" to "reconnect needed".
- Partial-join retry: only the failed participant relaunches; the ready
  agent stays attached, idle, and receives no work.
- Participant-only restart: restarting one agent leaves the other agent's
  process untouched.
- Idle-room reconciliation: a capture while the room is idle appends
  exactly once and is not lost.
- Scout failure: a `timed_out` item can be declined on its failure report
  and completion is not blocked.
- Capture/completion race: a capture racing the transition into
  `appendix_evaluation` is atomically frozen out (or lands in the
  snapshot), never half-appended.
- Terminal phase progression: `complete()` walks `original_work →
  appendix_evaluation → extension_work → closing`, and only `closing`
  invokes the terminal room-closing behavior.
- Approved oversized-patch retention: the scratch branch survives until
  extension completion, explicit rejection, or import into the session
  worktree.
- Schema migration: additive only; existing rooms stay readable.
- Patch isolation: an ancillary patch never lands without approval;
  nothing pushes or merges from scratch branches.
- Package provenance: usage and the completion package split main vs.
  ancillary work via `origin_kind`.
- Planning isolation: no repository mutation; writes confined to the
  disposable analysis area.
- Promotion without state loss: approval carries plan revisions,
  objections, assumptions, gates, repository/workspace context, and
  provenance into coordination.
- Duplicate approval / partial-failure recovery: one coordination session
  per plan; a crash between the promotion reservation and worktree
  creation resumes the reserved record on retry, never creating a second
  session.
- Source-branch movement after approval: the coordination worktree still
  branches from the recorded `inspection_sha`.
- Repository drift at approval: a baseline that moved past
  `inspection_sha` returns the plan to review; nothing executes on stale
  assumptions.
- Gate-materialization fidelity: each explicit acceptance criterion
  becomes its own gate — no `SPEC-01` collapse, no ID collisions.
- PLAN-READY invalidation: a human edit or a promoted dropbox item forces
  a revision and re-review.
- Post-ready dropbox race: capture freezes at approval; late items land in
  the coordination session's dropbox.
- Unsupported isolation adapter: Planning Mode is shown as unavailable,
  never silently downgraded to contract-only protection.
- Attempted approval with a blocking decision: refused until the decision
  is resolved or explicitly waived via a reviewed revision.

## Watch areas during implementation

1. Passive-doctor purity: probes must never trigger interactive prompts,
   browser popups, or provider charges; every probe is timeout-bounded and
   reports a truthful unknown when it cannot tell. The consented
   connection test is the only thing that ever invokes a provider, and it
   runs sandboxed.
2. One supervisor decision per failure: the participant-scoped recovery
   ladder must compose with the v0.4.0 restart flow, two-strike drop, and
   terminal-transition discipline (`manager.complete()`/`stop()` race
   rules) without double-recovery or drop races.
3. Critical-path isolation: ancillary rooms never touch the session
   worktree or canonical branch, never starve the main room's scheduling,
   and their stream volume respects the existing 0.75 s repaint caps;
   reconciliation adds no perceptible turn latency.
4. Appendix integrity: exactly-once append under the database constraint;
   the original spec's bytes and digest stay untouched; completion blocks
   on unevaluated appendix items and unmet extension gates only — a
   declined or failed item never blocks closing.
5. Join indicators track real phase transitions and always clear on ready
   or failure — no stuck "joining" states.
6. No accidental implementation in Planning Mode: filesystem/repository
   mutations beyond permitted inspection and the disposable analysis area
   remain technically prevented until approval.
7. Planning approval must be meaningful: PLAN-READY requires
   adversarial-review closure, not merely planner completion.
8. No state loss on promotion: approval preserves plan revisions,
   objections, assumptions, gates, repository/workspace context, and
   provenance when coordination begins.
9. No silent plan drift: implementation may adapt details, but material
   divergence from the approved architecture or scope must be recorded and
   governed.
10. Avoid ceremonial review: the plan reviewer must independently inspect
    enough repository state to evaluate whether the plan is actually
    executable and correctly ordered.
11. Do not over-plan: the goal is the minimum sufficiently defensible
    implementation plan, not exhaustive speculation. Stop when remaining
    objections are redundant, low-value, or explicitly classified
    nonblocking.
12. Preserve mode separation: Planning Mode determines what should be
    done; coordination determines whether it was implemented correctly.
